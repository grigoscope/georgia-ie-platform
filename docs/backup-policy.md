# PostgreSQL backup policy

## Цель

Резервные копии используются для восстановления данных PostgreSQL после ошибки приложения, повреждения базы, сбоя сервера или ошибочных административных действий.

## Частота

Рекомендуемый график:

- ежедневный backup;
- дополнительный backup перед обновлением приложения;
- дополнительный backup перед потенциально опасными миграциями или административными операциями.

## Срок хранения

Рекомендуется хранить:

- ежедневные копии — минимум 7 дней;
- недельные копии — минимум 4 недели;
- месячные копии — по требованиям владельца production-инфраструктуры.

## Место хранения

Backup не должен храниться только на том же сервере, что и основная PostgreSQL.

Минимально одна актуальная копия должна находиться во внешнем хранилище.

## Шифрование

При хранении backup за пределами доверенной инфраструктуры файл должен быть зашифрован.

Доступ к backup должен предоставляться только ответственным администраторам.

## Создание backup

```bash
./scripts/backup_db.sh
```

Копии сохраняются в:

```text
backups/
```

## Restore

```bash
./scripts/restore_db.sh backups/<backup-file>.dump
```

Перед restore рекомендуется создать backup текущего состояния базы.

## Проверка восстановления

Backup считается рабочим только после успешного тестового restore.

Тест восстановления необходимо выполнять периодически и после изменений backup-скриптов.

## Ответственность

Ответственный за production-инфраструктуру контролирует:

- регулярность создания backup;
- наличие свободного места;
- доступность внешних копий;
- успешность тестового восстановления;
- ограничение доступа к резервным копиям.

## Порядок восстановления

1. Остановить запись новых данных в приложение.
2. Создать backup текущего состояния, если база доступна.
3. Выбрать необходимую резервную копию.
4. Выполнить restore.
5. Применить актуальные миграции.
6. Запустить приложение.
7. Проверить healthcheck.
8. Проверить основные пользовательские сценарии.
9. Проверить Celery worker и Celery Beat.
10. Зафиксировать факт восстановления.
